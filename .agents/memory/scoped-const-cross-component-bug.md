---

## 증상
- 특정 화면 진입 시 흰 화면 또는 "페이지를 표시하는 중 오류가 발생했습니다" 같은 에러 바운더리 메시지만 뜸
- 브라우저 콘솔/에러 메시지: `X is not defined` (ReferenceError)
- 서버 API는 200 정상 응답하는데도 화면이 깨짐 → 데이터 문제가 아니라 렌더링(스코프) 문제라는 신호

## 원인
- 원래 모듈 최상단에 `const X = [...]`로 선언되어 여러 함수 컴포넌트가 자유롭게 참조하던 상수를,
  리팩터링(예: 데이터를 동적으로 바꾸는 작업) 과정에서 특정 컴포넌트 함수 내부의 지역 변수로 옮김
- 이때 같은 파일의 다른 함수 컴포넌트들(다이얼로그, 폼 등)이 여전히 그 이름을 참조하고 있으면,
  JS 스코프 체인 상 접근 불가능하지만 **esbuild/vite는 타입체크를 하지 않으므로 빌드/HMR은 통과**함 → 실제 그 컴포넌트가 렌더링되는 순간에만 런타임 크래시
- 특히 `{condition && <Dialog open={false} .../>}` 패턴처럼 다이얼로그가 `open=false`여도 컴포넌트 자체는 마운트되는 경우, "다이얼로그를 열지도 않았는데" 상위 조건(예: 세션 선택)만으로 크래시가 유발됨

## 어떻게 적용할까
- 상수를 지역 변수로 바꾸는 리팩터링을 할 때는 같은 파일 내 해당 이름을 쓰는 **모든** 함수 컴포넌트를 grep으로 확인하고, 각 컴포넌트에서 동일한 훅/로직으로 재계산하거나 prop으로 전달
- 이런 크래시는 TypeScript 타입 에러로도 안 걸러지고 API 테스트로도 못 잡음(순수 프론트 렌더링 스코프 문제) — 실제 브라우저에서 해당 화면을 열어보거나, 앱에 ErrorBoundary를 심어 에러 메시지를 노출시켜야 빠르게 찾을 수 있음
- 근본 대응: 앱 전역에 React ErrorBoundary가 없으면 이런 종류의 버그가 "원인 불명의 흰 화면"으로만 보고되어 진단이 매우 어려워짐 — ErrorBoundary를 항상 심어두는 것이 재발 시 즉시 원인 파악에 결정적
