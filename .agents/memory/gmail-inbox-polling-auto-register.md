## 패턴
- 기존에 발신용(outbound, nodemailer)으로 쓰던 Gmail 계정을 그대로 IMAP(imap.gmail.com:993)으로 재사용해서 수신함(INBOX)을 폴링할 수 있다. 별도 계정/앱 비밀번호를 새로 만들 필요 없음.
- `imapflow` + `mailparser`(simpleParser)로 원본 메시지(source)를 파싱하면 제목/본문 텍스트/첨부파일(이미지 포함)을 한번에 얻을 수 있다.
- node-cron으로 주기 폴링(예: 10분 간격). 서버 부팅 시 1회 스케줄 등록하는 파일을 만들고 `server/index.ts`에서 `import "./..."`로 사이드이펙트만 로드.

## 매칭 전략
- AI/정규식 기반 유연한 매칭보다, 사용자가 이미 알고 있는 고유 식별자(예: 작업지시번호)가 "이메일 제목이나 본문에 문자열로 그대로 포함되어 있는가"를 기준으로 매칭하는 게 오탐이 적고 사용자에게 설명하기도 쉬움. 후보 식별자 목록을 길이 내림차순으로 정렬해서 부분 포함 오매칭을 줄인다.

## 중복 처리 방지
- 마지막으로 처리한 IMAP UID를 DB(settings 키-값 테이블 등)에 저장해두고, 다음 폴링 때 `lastUid+1:*` 범위만 조회. UID는 메일함 내에서 단조증가하므로 재처리 방지에 안전하게 쓸 수 있다.

## 자동화 범위를 신중하게 제한
**Why:** 사용자가 "사진/사유는 자동 등록하되, 최종 승인(소명완료) 처리는 사람이 확인 후 하게 해달라"고 명시적으로 요구한 사례가 있었음 — 자동화 오류로 잘못된 완료 처리가 나갈 위험을 피하기 위함.
**How to apply:** 이메일/AI 등으로 자동 등록하는 기능을 만들 때, "데이터 등록"과 "상태를 완료/승인으로 바꾸는 것"을 별개 액션으로 분리하고, 후자는 사람이 명시적으로 트리거하게 남겨두는 것이 안전한 기본값. 사용자가 명확히 전체 자동화를 요구하지 않는 한 이 경계를 유지할 것.
