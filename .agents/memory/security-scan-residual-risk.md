## 규칙
의존성 취약점 스캐너가 "high"로 표시해도, 아래 경우는 실제 런타임 공격 표면이 없으므로 강제 업그레이드보다 근거를 확인하고 문서화하는 편이 안전하다.

- **pinned 하위 의존성**: 상위 패키지(A)가 취약 패키지(B)를 세미버 범위가 아니라 정확한 버전으로 고정(`"b": "1.2.3"`)한 경우, 우리가 B를 직접 상위 버전으로 설치해도 A는 여전히 자기 pinned 사본을 쓴다. `npm view <pkg> dependencies`로 확인. (예: mailparser/imapflow가 nodemailer/linkify-it을 자체 고정)
- **빌드 전용 도구 체인**: 취약 패키지가 네이티브 모듈 빌드(node-pre-gyp 등)에서만 쓰이고 요청 처리 경로에 없으면 실사용 리스크는 낮음 (예: canvas → node-pre-gyp → tar).
- **패치 미제공 패키지**: `xlsx` 같이 fix 버전이 없는 경우, 신뢰 가능한 입력만 처리하도록 범위를 제한하는 것으로 리스크를 인지·완화하고 완전 제거는 별도 논의 필요.
- **의도된 내부 통신**: Replit 오브젝트스토리지 사이드카처럼 컨테이너 내부 `127.0.0.1` 호출에 대한 "insecure HTTP" 경고는 외부 노출이 없으므로 수정 대상 아님.

**Why:** 이런 항목까지 억지로 메이저 업그레이드하면 (예: nodemailer 8→9, tar 6→7, uuid 8/9/10→11) 호환성 리스크만 커지고 실제 보안 이득은 없거나 미미하다.

**How to apply:** 보안 스캔 후 remediation 우선순위를 정할 때, 먼저 `npm ls <pkg>`로 트리 위치를 확인하고, 직접 의존성이면 패치, transitive/pinned/build-only면 실사용 경로를 추적한 뒤 고칠 수 없으면 replit.md 등에 근거와 함께 잔존 리스크로 기록한다.
